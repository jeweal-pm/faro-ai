# SPEC: OpenRouter TypeSafe Jev discovery routing

- **Status:** Implemented; a live Jev request is verified; product results remain blocked by the current GIS MCP endpoint returning HTTP 404
- **Date:** 2026-10-14
- **Decision:** [ADR-0019](../adr/0019-use-openrouter-typesafe-jev-decisions-api.md)
- **Related:** [Provider and request price limits](model-price-limits.md), [Live MCP product search](live-mcp-product-search.md), [Discovery shopping journey](0018-discovery-shopping-journey.md)

## Provider setup and eligibility

- Reuse the enabled OpenRouter connection configured in Backoffice. The AI service must not read an independent Jev key, URL, or model name from environment variables.
- Only the gateway reads and decrypts the provider API key. It sends the key to the private AI service in the signed internal request. The AI service uses the fixed HTTPS URL `https://openrouter.ai/api/alpha/decisions` with redirects disabled, proxy environment variables ignored, and a finite timeout.
- Jev 1.13 input pricing is currently `$0.042 / 1M tokens`; output is `$0 / 1M tokens`. Require the connection's maximum input price to be at least `$0.042 / 1M tokens`; output cap must be nonnegative. Also require an enabled connection, a complete encrypted credential, and deployment permission for external OpenRouter use.
- Do not increase a connection's price caps automatically. If no connection passes, `decision_api_key` is empty and the AI service uses its existing deterministic route. Backoffice reports Jev eligibility without exposing credential contents.
- Reserve one FAROAI model credit when an eligible Jev call or generation candidate may be used. Settle it when Jev returns a response or a generation model is used; refund it when neither is used. Credits are not USD and do not reconcile the actual OpenRouter invoice.

## Typed Decisions request

Use `model: "typesafe/jev-1.13"`, `questions` with TypeSafe `choice` types, and `state` containing the sanitized user prompt. The request may ask for:

- Intent: live MCP, local catalog, knowledge, or chat. Prefer live MCP for product shopping when a current, approved `search_products` tool exists.
- Source: only source IDs present in this request and their approved tools.
- Generation candidate: only paid, current, in-cap candidates supplied by the gateway; `none` is available when no generated prose is needed.
- Product type, jewelry style, recipient, and outfit context from a fixed vocabulary.
- Explicit gemstone-shape exclusions from the fixed GIS shape vocabulary.

Jev returns `answers.<question>.choice`. Accept only a string that exactly matches the submitted criteria key. Do not parse generated text, confidence as authorization, or any provider-supplied routing target.

For recommendation prompts with meaningful preferences or exclusions, Jev should select the lowest-priced suitable paid candidate from the already price-filtered list. A plain category lookup may select `none` when verified product cards alone satisfy the request. Candidate descriptions include their eligible input/output rates; Jev does not receive endpoint URLs or credentials.

## GIS search query

- Keep the shopper's positive query meaning and remove only a validated explicit negative shape phrase before sending `query` to the approved GIS `search_products` tool.
- Send `stone_shape_exclude` only through the optional MCP `filters` argument when `tools/list` advertises that argument; otherwise use the legacy query-only compatibility path and filter visible shape data after retrieval.
- Append server-defined phrases only for validated choices. Examples: `ring`, `alluring glamorous evening style`, `for girlfriend`, and `recipient wears black clothing`.
- The `dark` jewelry style maps to `dark or black jewelry`; black clothing context maps to an outfit phrase and must never become a jewelry-color constraint.
- Pass the existing language value. Keep endpoint, API key, tool name and tool arguments under FaroAI control.
- Trust only the validated MCP product response contract in [Live MCP product search](live-mcp-product-search.md). Jev preferences do not prove availability, price, material, or a product match.

## Failure handling and data boundaries

- Network errors, non-success responses, and malformed decisions use the existing deterministic route; log only the event and tenant ID, never request text, response body, or credential.
- A successful Decisions response counts as Jev usage even if an answer choice is malformed, so its credit reservation is settled. Validate choices before using them.
- Do not cache decisions. Do not persist prompts, decisions, MCP product results, or generated answers to Qdrant or training through this request path.
- `decision_used` is returned separately from `ai`, which continues to mean prose was generated by a normal eligible model.

## Backoffice presentation

- On `/admin/providers`, show whether each connection can be used for Jev and explain that an enabled OpenRouter connection needs a saved key and input cap of at least `$0.042 / 1M tokens`.
- Keep the existing `$10` maximum for all operator-entered rate limits. A zero cap remains a valid disabled setting.
- Do not add a model picker for Jev. `typesafe/jev-1.13` is the fixed decision model and is not a generated-text candidate.

## Acceptance criteria

- [x] The adapter calls the OpenRouter Decisions endpoint and pins `typesafe/jev-1.13`.
- [x] Credentials come from the encrypted Backoffice provider connection and are not logged or returned to the browser.
- [x] A provider cap below Jev's input rate prevents the network call.
- [x] MCP source and generation-model choices are resolved only against server-provided allow-lists.
- [x] Jev-selected, validated product preferences enrich the GIS query without replacing the original prompt.
- [x] Outfit color and jewelry color are kept distinct.
- [x] Jev usage is reported separately from generated prose and included in credit settlement.
- [x] Live TypeSafe Jev Decisions request from the Discovery UI: OpenRouter returned HTTP 200 and the corresponding gateway credit reservation settled.
- [ ] End-to-end product cards from the Discovery UI: blocked because the configured GIS MCP endpoint returns HTTP 404 during Streamable HTTP initialization; Jev was called, but GIS could not return products.
