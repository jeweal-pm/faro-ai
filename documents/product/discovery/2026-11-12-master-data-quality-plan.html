ข้อเสนอสำหรับ Supplier, Location, Product และ Voucher ที่สร้างจากเอกสารหรือ prompt โดยให้ AI ช่วยเตรียมงาน แต่ GIS ยังเป็นแหล่งข้อมูลหลัก

วันที่ 12 พ.ย. 2026ขอบเขต: FaroAI + GIS MCPเริ่มจาก document-to-PO

หลักที่ควรยึด

อย่าสร้างเพื่อแก้ mapping ที่ผิด

ถ้ารายการมีอยู่แล้ว ให้ค้นและเลือก record เดิมจาก GIS ก่อน หากค้นไม่ตรงหรือมีหลายรายการ ให้หยุดถาม ห้ามเลือก record ที่ “คล้ายที่สุด” เอง

แยก “จับคู่” กับ “สร้างใหม่”

ผู้ใช้เลือกได้ชัดเจนว่าจะ map ไปยัง Supplier/Location เดิม หรือเสนอสร้างใหม่ การเลือก map ต้องปิดทาง create ใน runtime

AI เสนอ ผู้ใช้ยืนยัน GIS เขียน

ตรวจชื่อ รหัส ประเทศ ที่อยู่ และข้อมูลซ้ำก่อนแสดง preview การแก้ฟอร์มหรือ OCR ไม่ใช่การอนุมัติสร้าง master

เก็บ alias แยกจาก master

ชื่อที่ OCR อ่านคลาดหรือชื่อเรียกในเอกสารควรเป็น mapping/alias ที่ตรวจสอบได้ ไม่ควรสร้าง Supplier ใหม่ทุกครั้งที่เจอรูปแบบชื่ออีกแบบ

ข้อควรระวัง: อย่า auto-merge หรือ auto-delete master จากคะแนน similarity เพียงอย่างเดียว เพราะอาจรวมบริษัท สาขา หรือสินค้า distinct เข้าด้วยกัน

Flow ที่แนะนำ

อ่านเอกสารเก็บ OCR และตำแหน่งหลักฐานไว้แยกจากค่าที่แก้
ค้น GISจับคู่ exact code ก่อน แล้วเทียบชื่อ/ที่อยู่ พร้อมตรวจผลค้นครบ
ให้คนแก้ mappingเลือก master เดิม หรือระบุสร้างใหม่ แก้ line/SKU/จำนวน/ราคาได้
ตรวจ duplicate + previewตรวจ required fields, tenant, สถานะ และ record ซ้ำอีกครั้ง
ยืนยันและ auditสร้างเฉพาะรายการที่ยืนยัน บันทึก actor/source/hash/result

แผนงานเป็นระยะ

ระยะ 1 · ตอนนี้
  • ฟอร์ม PO preparation แก้ Supplier/Location และแถวสินค้าได้
  • ผู้ใช้ระบุ “map existing” หรือ “create new” แยกกัน
  • บันทึก correction แยกจาก OCR ต้นฉบับ และส่งเตรียม GIS preview ซ้ำได้
  • บล็อก create เมื่อผู้ใช้เลือก map existing; master ใหม่ยังมี confirmation แยก
ระยะ 2 · GIS-backed mapping
  • เปลี่ยนช่องชื่อ/รหัสเป็นค้นหา dropdown จาก GIS ตาม tenant และ master type
  • แสดง code, ชื่อ, สถานะ, ที่อยู่ และข้อมูลแยกสาขาเพื่อให้เลือกถูก record
  • ส่ง ID ที่ผู้ใช้เลือกกลับมา แต่ backend ต้องค้นยืนยัน ID/tenant/status ซ้ำก่อน preview
  • มี duplicate warning แบบ exact code, normalized name และที่อยู่ โดยไม่ auto-merge
ระยะ 3 · ควบคุมการสร้าง
  • เพิ่ม master draft/quarantine ถ้า GIS รองรับ; ถ้าไม่รองรับ ให้ใช้ preview และ confirmation ที่ FaroAI คุม
  • Idempotency key ต่อ operation เพื่อป้องกัน double click/retry สร้างซ้ำ
  • ตรวจ code ซ้ำทั้งตอนแสดง preview และก่อน write; ตรวจ inactive/archived แยกจาก not found
  • จำกัดสิทธิ์สร้าง master แยกจากสิทธิ์อ่านและสร้าง PO
ระยะ 4 · ดูแลระยะยาว
  • แดชบอร์ด duplicate candidates และงานค้าง review แยกตาม tenant
  • กระบวนการ merge/archive ที่มีผู้อนุมัติและย้อนดู audit ได้
  • Alias ที่จำได้ต้อง tenant-scoped, มีผู้อนุมัติ, วันหมดอายุ และลบได้; ห้ามนำ PII/ข้อมูลราคาไปเป็น global learning
  • วัดอัตรา duplicate, create ที่ถูกยกเลิก, mapping ที่แก้, preview fail, และเวลาปิดงาน

กฎป้องกันข้อมูลขยะที่ควรทำเป็นระบบ

จุดควบคุมข้อเสนอ
ก่อนเสนอสร้างค้น code แบบ exact; ค้นชื่อ normalized; ตรวจที่อยู่/ประเทศเพื่อเตือนความคล้าย แต่ให้คนตัดสิน
ตอน reviewแสดงข้อมูลจากเอกสารเทียบกับ GIS และช่องที่ไม่ตรง พร้อม source evidence; ค่าไม่ทราบให้ว่าง ไม่เติมเดา
ก่อนเขียนทำ duplicate check ซ้ำบน backend, ตรวจสิทธิ์และ tenant, ใช้ idempotency, ปฏิเสธข้อมูลไม่ครบ
หลังเขียนอ่านกลับจาก GIS เพื่อยืนยัน ID/status; เก็บ audit แบบไม่เก็บ OCR เต็มหรือ credential
ข้อมูลเก่ารายงาน duplicate และเสนอ merge/archive; ไม่ลบหรือรวมอัตโนมัติ

สิ่งที่ต้องประสานกับทีม GIS MCP

ระยะถัดไปควรมี read API ที่คืนรายการ Supplier/Location/Product แบบค้นหาแบ่งหน้า พร้อม code, normalized identity, status และผลค้นว่า complete หรือไม่ รวมทั้ง create endpoint ที่รองรับ idempotency และคืนเหตุผล duplicate อย่างชัดเจน ถ้า GIS มี uniqueness constraint อยู่แล้ว ให้ FaroAI ใช้ผลนั้นและแสดงข้อความแก้ไขได้ แทนการสร้างทางลัดข้าม GIS

ลำดับที่แนะนำ: ทำ form + retry ให้ผู้ใช้แก้เคสปัจจุบันได้ก่อน → เพิ่ม GIS-backed selectors → เพิ่ม duplicate dashboard และ lifecycle control หลังยืนยัน schema/ข้อจำกัดของ GIS
เอกสารนี้เป็นข้อเสนอและแผนงาน ไม่ได้สั่ง merge, archive หรือลบ master ที่มีอยู่
