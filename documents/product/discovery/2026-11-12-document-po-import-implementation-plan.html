เริ่มจากของที่มี

มีแล้ว

รับไฟล์และ OCR แยก worker

Compose profile document-import; worker ทำงานทีละงาน จำกัด 0.20 CPU / 512 MiB, ไม่มี port และต่อได้เฉพาะ PostgreSQL ผ่าน network ภายใน

มีแล้ว

เก็บต้นฉบับและข้อมูลตรวจแยกกัน

ไฟล์เข้ารหัส เก็บต้นฉบับไม่เกิน 24 ชั่วโมง และข้อมูล review/OCR ไม่เกิน 7 วัน ตามเอกสารปัจจุบัน

มีแล้ว

ฟอร์มแก้ PO preparation และส่งใหม่

แก้ Supplier, Location, SKU, จำนวน, ราคา และสกุลเงินได้โดยไม่อัปโหลดซ้ำ; correction แยกจาก OCR เดิมและการส่งใหม่ต้องทำ GIS matching/preview ใหม่

ขั้นถัดไป

เปลี่ยนการพิมพ์ชื่อเป็น GIS-backed selection

ช่อง mapping รุ่นแรกยังใช้ชื่อ/รหัสแบบ exact text; ทำ dropdown ที่ค้น master ของ tenant และผูก GIS ID ที่ backend ตรวจซ้ำได้

ข้อจำกัดที่ต้องสื่อให้ตรง: เพดาน Docker เป็นค่าจำกัดสูงสุด ไม่ใช่ผลวัดการใช้ CPU/RAM จริง และการเปิด worker ไม่ได้แปลว่า PO ถูกสร้างแล้ว ผู้ใช้ต้องตรวจ preview และยืนยันการเขียนแยกต่างหาก

Flow ที่ผู้ใช้ทำได้ในหน้าเดียว

1แนบเอกสาร

รับ PDF/รูปที่รองรับ; ตรวจชนิดและขนาดก่อนจัดคิว

2OCR + แยก field

อ่านเอกสารใน worker แยก; ข้อความเอกสารเป็นข้อมูล ไม่ใช่คำสั่ง

3แก้และจับคู่

แก้ค่าที่อ่านผิด เลือก Supplier/Location/Product จาก GIS

4ตรวจความครบ

ห้ามเดา tax, country, SKU, quantity หรือ unit price

5ดู GIS preview

ตรวจผู้ขาย, ปลายทาง, รายการ, ยอดรวมและสถานะ

6ยืนยันสร้าง PO

สร้าง PO pending approval; ไม่อนุมัติหรือรับสินค้าแทนผู้ใช้

แผนพัฒนาเป็นขั้น

ฐานที่ทำแล้ว
1 · แก้แล้วส่งใหม่
  • มีฟอร์มแก้ข้อมูล PO และลองเตรียมใหม่จากเอกสารเดิม
  • เก็บ OCR ต้นฉบับไว้เทียบกับค่าที่ผู้ใช้แก้
  • ทุกครั้งที่ส่งซ้ำต้องค้น GIS และสร้าง preview ใหม่; ห้ามใช้ preview เก่า
  • Map existing ต้องไม่เรียก create master; Create new ยังต้องผ่าน review/confirmation ของ GIS แยก
2 · ทำ mapping ให้เลือกง่าย
  • เพิ่ม GIS search selectors สำหรับ Supplier, Location, Product และ Voucher; ค้นแบบแบ่งหน้าและแสดง code, ชื่อ, สถานะ/สาขา
  • เลือก record แล้วส่ง ID กลับ API; backend ตรวจ tenant, active status และความตรงกับข้อความในเอกสารซ้ำ
  • ถ้า exact match ไม่พบหรือพบหลายตัว ให้แสดงตัวเลือก/คำถาม; ห้ามเลือก “ใกล้เคียงที่สุด” อัตโนมัติ
  • แสดงหลักฐานจากเอกสารข้าง field เพื่อให้ผู้ใช้เห็นว่า AI อ่านค่าจากตรงไหน
3 · ป้องกัน master ซ้ำ
  • ค้น exact code ก่อน แล้วตรวจ normalized name, country และ address เป็น duplicate warning
  • แยกปุ่ม “เลือกของเดิม” กับ “ขอสร้างใหม่”; ก่อน create ตรวจ required fields และค้นซ้ำอีกครั้งที่ server
  • สร้างแต่ละ master ผ่าน GIS API/MCP ที่มี permission แยกและ idempotency; อ่านกลับ record เพื่อยืนยัน
  • ไม่ auto-merge, archive หรือลบ Supplier/Location/Product; ทำรายงาน candidate ให้คนตรวจ
4 · เขียน PO อย่างควบคุม
  • ใช้ preview แบบ no-write ตรวจ master IDs, currency, tax, quantity, ราคาต่อหน่วยและยอดรวม
  • ใช้ confirmation ที่ผูกกับ tenant, actor, document version และ preview hash; เปลี่ยนค่าหลัง preview แล้วต้อง preview ใหม่
  • กัน double-submit/retry ด้วย idempotency; ถ้า timeout หลัง write ให้แสดงสถานะไม่แน่ชัดและตรวจ GIS ก่อน retry
  • หลังสร้างให้อ่าน PO กลับจาก GIS และแสดงเลขที่/สถานะ pending approval; ไม่เรียก approve หรือ receive
5 · ทดสอบและเปิดใช้
  • ทดสอบ fixture ที่อนุญาต: PDF มี text, scan ไทย/อังกฤษ, หลาย layout, field หาย, supplier/location ไม่ตรง, สินค้าชื่อคล้ายและ SKU ขัดกัน
  • ทดสอบ duplicate, tenant isolation, สิทธิ์อ่าน/เขียน, ผู้ใช้ยกเลิก, timeout, ส่งซ้ำ, ลบและ TTL
  • เริ่ม pilot tenant เดียวและจำกัด concurrency; เก็บเฉพาะ latency/error/queue depth/resource metrics ที่ไม่บันทึก OCR หรือ PII
  • ขยายจำนวน worker เมื่อ metric แสดงว่า queue หรือเวลารอเกินเป้าหมาย ไม่ขยาย CPU/RAM แบบเดา

กติกาความปลอดภัยที่เป็นเงื่อนไขผ่านงาน

แยก tenant และสิทธิ์

ใช้ tenant/actor จาก session ที่ตรวจแล้ว; แยก permission ดู master, สร้าง master, สร้าง PO, approve PO และรับสินค้า

ไฟล์และ OCR เป็นข้อมูลไม่น่าเชื่อถือ

ตรวจ signature, MIME, page/pixel/byte limits; ปฏิเสธ format ที่ไม่รองรับ; ไม่ให้ prompt ใน PDF เปลี่ยนคำสั่งระบบหรือเรียก tools เอง

Worker แยกและจำกัด

คง worker แบบ non-root, read-only root FS, capabilities dropped, no-new-privileges, internal DB-only network, tmpfs จำกัด และไม่มี provider/GIS credentials

เข้ารหัสและลบตามกำหนด

แยก encryption key จาก API secrets; source 24h, review data 7d ตาม policy; การลบต้องลบ source, previews, OCR และ corrections พร้อมตรวจผล

ห้ามสร้างจาก OCR โดยตรง: การอ่านไฟล์หรือกดส่งเข้าคิวไม่เท่ากับการอนุญาตสร้าง GIS master/PO ทุกการเขียนต้องแสดงผลที่กำลังจะสร้างและให้ผู้ใช้ยืนยันตามขอบเขตที่กำหนด

ขั้นนำขึ้น EC2 แบบปลอดภัย

ลำดับนี้เป็น deployment plan สำหรับ pilot ก่อน ยังไม่ใช่คำสั่งให้เปิด production ทันที

1 · เตรียม AWS
  • เลือก Region และ Availability Zone ตามที่ผู้ใช้/ข้อมูลอยู่; ทำ budget alert ก่อนสร้างทรัพยากร
  • ให้ EC2 อยู่ private subnet; เปิดรับ HTTPS 443 ผ่าน load balancer หรือ VPN ตามรูปแบบแอป
  • ปิด public SSH; ใช้ AWS Systems Manager Session Manager และ IAM role แบบ least privilege
  • สร้าง EBS gp3 แบบ encryption at rest, กำหนด snapshot/retention และทดสอบ restore
2 · เตรียม secrets
  • สร้าง secrets แยก dev/staging/prod ใน AWS Secrets Manager หรือ SSM Parameter Store แบบ SecureString ตาม policy
  • สร้าง document encryption key และ database worker credential ใหม่สำหรับ environment นี้; ห้ามคัดลอกจาก local .env หรือ commit ลง Git
  • ให้เฉพาะ instance role ที่จำเป็นอ่าน secret; ห้ามใส่ secret ใน user-data, image layer, shell history หรือ logs
  • กำหนดแผน rotation/backup ของ key ก่อนเก็บเอกสารจริง เพราะการสูญ key อาจทำให้ถอดรหัสไฟล์ที่ยังอยู่ไม่ได้
3 · deploy staging
  • ติดตั้ง OS/Docker จากแหล่งทางการและอัปเดต security patches; ใช้ image ที่ pin version/digest และ deploy จาก artifact ที่ตรวจแล้ว
  • ตั้งค่า database, Redis, Qdrant, app และ network ตาม Compose/architecture ที่ตรวจแล้ว; อย่าเปิด PostgreSQL, Redis, Qdrant หรือ worker port สู่ internet
  • สำรองฐานข้อมูลก่อน migration; รัน migration 021 ตามขั้นตอน deployment และ provision worker ด้วย DB role แบบจำกัด ไม่ใช้ PostgreSQL owner
  • เปิด Compose profile document-import แต่คง FaroAI document-import feature flag ปิดไว้จน readiness ผ่าน
4 · ตรวจ readiness
  • ตรวจ API, DB, Redis, Qdrant และ worker health/heartbeat; ตรวจว่า worker เห็นเฉพาะ DB network และไม่มี published port/egress
  • ตรวจ file volumes เป็น private, encryption key ถูกอ่านจาก secret store, TTL sweeper ทำงาน และ logs ไม่มี OCR/PII/secret
  • ลอง fixture สังเคราะห์ใน staging: รับไฟล์ → review/correction → GIS preview; ยังไม่ยืนยัน write เพื่อทดสอบการปฏิเสธ input ผิด
  • ลอง tenant อื่นอ่าน job ไม่ได้, role worker อ่าน/เขียนได้เฉพาะงานที่กำหนด และ deletion/expiry ทำงานตามกำหนด
5 · เปิด pilot
  • เปิด feature ให้ tenant ทดลองกลุ่มเล็กก่อน ตั้ง queue limit และ concurrency OCR เริ่มที่ 1 worker
  • ใช้ document synthetic หรือเอกสารที่ได้รับอนุญาต; ทดสอบ PO ที่ master ไม่ตรง, master หาย, duplicate และ timeout
  • ผู้ใช้ต้องเห็น field/mapping/preview และยืนยันก่อน GIS write; ตรวจ PO ที่อ่านกลับว่าตรงและเป็น pending approval
  • ติดตาม CPU/RAM, disk, queue depth/wait, OCR duration, failure rate, deletion lag และค่าใช้จ่าย โดยไม่เก็บเนื้อหาเอกสาร
6 · ขยายหรือ rollback
  • ขยาย worker/EC2 เมื่อกราฟและ queue SLA แสดงคอขวดต่อเนื่อง; เพิ่มทีละจุดและวัดซ้ำ ไม่เปิด parallelism สูงโดยไม่มี tenant fairness
  • Rollback: ปิดรับงานใหม่ก่อน, drain หรือหยุด worker อย่างปลอดภัย, ปิด feature flag แล้วค่อยย้อน app image
  • ห้ามใช้ docker compose down -v หรือทิ้ง EBS volumes เพื่อ rollback; เก็บฐานข้อมูลและ document volumes จนตรวจสถานะงานและ retention เสร็จ
  • ถ้ามีผล GIS write ไม่แน่ชัด ให้ค้นยืนยันใน GIS ก่อน retry; อย่าสร้าง PO ซ้ำจากการ retry อัตโนมัติ
เงื่อนไขก่อน production: staging walkthrough ผ่าน, backup restore ทดสอบได้, secret rotation/retention/incident owner พร้อม, migration มี rollback/recovery procedure และผู้ดูแลอนุมัติค่าใช้จ่าย/monitoring แล้ว

ไฟล์ Docker ที่ใช้ และคำสั่งจริง

สำหรับ EC2 ใช้ docker-compose.yml ตัวเดียว
docker-compose.local.yml เป็น override สำหรับเครื่อง dev เท่านั้น มี hot reload, bind mount source และเปิด Qdrant dashboard บน loopback; อย่านำไฟล์นี้ไปรันบน EC2

คำสั่งด้านล่างให้รันบน Ubuntu EC2 จากโฟลเดอร์ root ของ FaroAI (ตัวอย่าง /opt/faroai). ต้องติดตั้ง Docker Engine และ Compose v2 แล้ว. Compose ใน repo นี้อ่านค่าจาก process environment และไฟล์ .env; มันไม่ได้ดึง secret จาก AWS Secrets Manager เอง ดังนั้น deployment automation ต้องดึง secret แล้วเขียน environment file ที่จำกัดสิทธิ์ (เช่น mode 0600) ก่อนเรียก Compose. ห้ามใช้ secret จาก local dev หรือ commit ไฟล์นี้

docker --version
docker compose version
sudo systemctl enable --now docker

เปิด Docker daemon ให้เริ่มอัตโนมัติเมื่อ EC2 boot. คำสั่งสองบรรทัดแรกใช้ยืนยันว่ามี Docker Engine และ Compose v2

docker compose -f docker-compose.yml ps -a
docker compose -f docker-compose.yml logs --tail=100 postgres migrations api

คำสั่งนี้ build/start บริการหลักตาม base Compose และรัน migration service ตาม dependency รวม migration 021_business_document_intake. Worker ยังไม่เริ่ม เพราะอยู่ใน profile แยก และ feature flag มี default เป็นปิด. ตรวจ migration exit code 0 และ API healthy ก่อนเปิดรับเอกสารจริง

2 · เตรียมสิทธิ์ฐานข้อมูล worker แบบจำกัด

bash infra/postgres/provision-document-import-worker.sh

รันหลัง migration 021 สำเร็จและตั้ง FAROAI_DB_PASSWORD ใน .env แล้ว Script สร้าง/หมุนรหัส login เฉพาะ worker แล้วเขียน FAROAI_DOCUMENT_IMPORT_DATABASE_URL ลง .env ด้วย permission 0600; script นี้ไม่เปิด feature, ไม่ตั้ง encryption key และไม่ start worker

3 · ตั้ง encryption key และเปิด worker เมื่อพร้อมทดสอบ

สร้าง secret แยกสำหรับ deployment นี้ใน Secrets Manager/SSM แล้วใส่ค่า Base64 ที่แทนข้อมูลสุ่ม 32 bytes ลง FAROAI_DOCUMENT_IMPORT_ENCRYPTION_KEY ใน environment file ที่ Compose อ่านได้. ถ้าต้องสร้าง key ใหม่ ใช้คำสั่งนี้ใน terminal ที่ปลอดภัย แล้วบันทึกค่าที่ได้เข้า secret store โดยไม่ใส่ใน Git หรือ log:

openssl rand -base64 32

ตั้ง FAROAI_DOCUMENT_IMPORT_ENABLED=true เฉพาะเมื่อ worker, key, DB role และ storage/retention พร้อม

docker compose -f docker-compose.yml --profile document-import config --quiet
docker compose -f docker-compose.yml --profile document-import up -d --build document-import-worker
docker compose -f docker-compose.yml --profile document-import ps -a
docker compose -f docker-compose.yml --profile document-import logs --tail=100 document-import-worker
docker compose -f docker-compose.yml up -d --no-deps --force-recreate api
curl -fsS http://127.0.0.1:3000/health/ready

เริ่ม worker และ dependencies ที่จำเป็นก่อน แล้ว recreate API เพื่อให้อ่าน feature flag ใหม่. Worker ไม่มี published port และเชื่อมเฉพาะ internal DB network. ตรวจ worker logs/heartbeat, API readiness, expiry cleanup และทำ staging fixture end-to-end ก่อนให้ผู้ใช้ลองจริง

4 · คำสั่งตอนเปิดเครื่อง หรือกู้ stack หลังหยุดเอง

บริการตั้ง restart: unless-stopped; container ที่เคย start จะกลับมาทำงานเมื่อ Docker daemon/เครื่อง reboot. ถ้าสั่ง compose stop, compose down หรือยังไม่เคยสร้าง worker จาก profile ให้รันจาก project root:

cd /opt/faroai
docker compose -f docker-compose.yml --profile document-import up -d
docker compose -f docker-compose.yml --profile document-import ps -a
curl -fsS http://127.0.0.1:3000/health/ready

ถ้ายังไม่เปิด document import หรือไม่ต้องการ worker ให้ใช้ docker compose -f docker-compose.yml up -d โดยไม่มี profile. ไม่ต้อง build ทุกครั้งที่ boot; ใช้ --build เมื่อ deploy source/image รุ่นใหม่เท่านั้น

5 · คำสั่งสำหรับเครื่อง dev

cd /home/joke/dev/faroai
docker compose -f docker-compose.yml -f docker-compose.local.yml --profile document-import config --quiet
docker compose -f docker-compose.yml -f docker-compose.local.yml --profile document-import up --build -d
docker compose -f docker-compose.yml -f docker-compose.local.yml --profile document-import ps -a

ใช้สองไฟล์นี้เฉพาะ development เพราะ override เปิด reload/bind mount และเปลี่ยน resource limits. ถ้าจำเป็นต้องเรียก provider ภายนอก ให้เพิ่ม -f docker-compose.hosted.yml ตามการตั้งค่า egress ที่อนุมัติ; OCR worker อย่างเดียวไม่ต้องใช้ hosted overlay

ดู log และหยุดโดยไม่ลบข้อมูล

docker compose -f docker-compose.yml --profile document-import logs --tail=100 api document-import-worker
docker compose -f docker-compose.yml --profile document-import stop document-import-worker
docker compose -f docker-compose.yml stop

Rollback: หยุด intake/worker ก่อน, ตั้ง FAROAI_DOCUMENT_IMPORT_ENABLED=false แล้ว recreate API. ห้ามใช้ docker compose down -v เพราะจะลบ named volumes ที่เก็บ database และไฟล์ใน retention period. คู่มือนี้เป็นเอกสาร ไม่ได้รันคำสั่งกับ EC2 หรือเปลี่ยน runtime

เกณฑ์ก่อนเรียกว่า “พร้อมใช้”

หัวข้อผ่านเมื่อ
ความถูกต้องPO ที่ได้ตรง supplier/location/SKU/จำนวน/ราคาในเอกสาร; ไม่มีการ fallback ไป Ham หรือ master อื่นเมื่อเอกสารระบุคนละรายการ
ไม่มีข้อมูลขยะกรณี master ไม่พบ/คลุมเครือจะแสดงให้แก้หรือหยุด; การสร้าง master ใหม่แยกจากการ map และมี duplicate/idempotency checks
ไม่เขียนโดยไม่ตั้งใจpreview ไม่เขียนฐานข้อมูล; ต้องยืนยันค่าชุดเดียวกับ preview ก่อนสร้าง PO; PO ที่สร้างเป็น pending approval เท่านั้น
ความลับและ retentionทดสอบ tenant isolation, สิทธิ์, encryption, ลบข้อมูล และ TTL; logs ไม่มี raw OCR, ไฟล์ หรือ credential
ทรัพยากรและคิววัด CPU/RAM peak, OCR duration, queue wait, failure/retry และ disk growth ด้วย fixture ที่อนุญาต แล้วค่อยกำหนด capacity/concurrency

  • AWS M7i/M7i-flex overview — ขนาด, network/EBS และ Flex baseline performance
