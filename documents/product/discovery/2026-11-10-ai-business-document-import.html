Flow ที่ผู้ใช้จะเห็น

จากไฟล์ต้นฉบับ → draft ที่ตรวจสอบได้ → GIS preview → ยืนยันรายการเดียวอย่างชัดเจน

1. แนบเอกสารใช้ปุ่ม attachment ในแชท เลือก PDF หรือภาพ; ระบบผูก actor, tenant และ hash ของไฟล์
2. ตรวจไฟล์ตรวจ file signature, malware, ขนาด, หน้า, corruption และ active content
3. จำแนกเอกสารPO, quotation, invoice, receipt หรือ unknown พร้อมภาษาและความมั่นใจ
4. ดึงข้อมูลแยก header และ line items ตาม schema พร้อมข้อความและตำแหน่งต้นทาง
5. ตรวจเงื่อนไขคำนวณยอด, ตรวจซ้ำ, หาค่าขาด/ขัดแย้ง และถาม GIS แบบ read-only
6. ตรวจทานดูต้นฉบับคู่กับตาราง แก้ไขค่าความมั่นใจต่ำ เลือก GIS master ที่ถูกต้อง
7. GIS previewส่งเฉพาะ schema/operation ที่ tenant มีสิทธิ์ แล้วแสดง preview ล่าสุด
8. ยืนยันและติดตามผู้ใช้ยืนยัน; gateway ตรวจซ้ำและเขียนครั้งเดียว แสดงสถานะ/เลขอ้างอิง

ทำ pipeline นำเข้าเป็นแกนกลาง แล้วใช้ทะเบียนชนิดเอกสาร (Document Type Registry) กำหนด schema และกฎของแต่ละชนิด จึงเพิ่มชนิดใหม่ได้โดยไม่ต้องเขียน upload/OCR/review ใหม่ทุกครั้ง

ข้อมูลที่ทะเบียนเก็บต่อหนึ่งชนิด

รหัสชนิดและชื่อเรียกหลายภาษา · family/direction · schema version และ required/optional fields · extraction guidance · deterministic validations · evidence requirements · duplicate keys · format ที่ผ่านการทดสอบ · GIS read/preview/write mapping และ permission · evaluation fixtures · owner และ support status

1 · รู้จักชนิด

จำแนกได้ พร้อมรองรับ alias และ `unknown`; ยังไม่ถือว่าดึงครบหรือทำรายการได้

2 · ดึงและตรวจได้

มี schema, evidence, validation และตัวอย่างประเมิน; แสดง draft ให้คนตรวจ

3 · GIS operation พร้อม

เปิด preview/write แยกตาม tool, tenant permission และการยืนยันของผู้ใช้

“เรียนรู้” แบบควบคุม: เมื่อผู้ใช้แก้และยืนยัน ระบบบันทึก alias/layout hint ในขอบเขต tenant เพื่อช่วยงานถัดไปได้; การเพิ่มชนิดหรือเลื่อนสถานะรองรับต้องผ่านการ review schema, GIS mapping และ evaluation ก่อน ไม่เปลี่ยนความสามารถหรือฝึก model อัตโนมัติจากไฟล์ดิบ

แบ่งงานให้เหมาะกับ AI และโค้ด

จัดเส้นทาง PDF และภาพให้จ่ายเท่าที่จำเป็น

PDF มี text layer

ลองดึงข้อความจาก PDF ก่อน ถ้าข้อความครบและอ่านได้ ให้ข้าม OCR แล้วส่งต่อเข้า classifier/extractor

PDF สแกนหรือผสม

ตรวจเป็นรายหน้า: OCR เฉพาะหน้าที่ไม่มี text layer หรือข้อความใช้ไม่ได้ ไม่ต้อง OCR ทั้งไฟล์ซ้ำ

ภาพที่แนบ

เริ่มจากตรวจว่าเป็นเอกสารธุรกิจหรือภาพสินค้า ถ้าแยกไม่ชัด ให้ถามผู้ใช้ว่า import เอกสารหรือค้นหาสินค้า

จำแนกแบบประหยัด: ใช้สัญญาณจาก PDF/text/OCR และรูปแบบหน้าเป็นด่านแรก แล้วให้ model ที่ Jev เลือกช่วยเฉพาะกรณีไม่ชัดหรือจำเป็นต้องเข้าใจภาพ อย่าเรียก AI แยกหลายรอบเพื่อทำงานที่รวมเป็นรอบเดียวได้

OCR แปลงภาพตัวอักษรเป็นข้อความ แต่ไม่ได้ตัดสินความหมายของเอกสารหรือยืนยันข้อมูล GIS การอ่าน PDF แบบผสมต้องเก็บ page evidence เพื่อให้ผู้ใช้ย้อนดูแต่ละค่าที่ระบบดึงออกมาได้

ลดต้นทุนโดยไม่ทำให้ tenant หนึ่งรอกันทั้งระบบ

ต้นทุนต่อไฟล์

ใช้ text extraction ก่อน; OCR เฉพาะหน้าที่ต้องใช้; ใช้ model ตามความยากและ price policy; ส่งเฉพาะข้อความ/ภาพที่จำเป็น; escalate เฉพาะ field ที่ยังไม่มั่นใจ

OCR กับ embedding

เป็นคนละงาน: OCR อ่านตัวอักษรจากภาพ ส่วน embedding ช่วยค้นความคล้าย ไม่ได้ดึง field จากเอกสาร การนำเข้าธุรกรรมไม่จำเป็นต้อง embed เอกสารทุกใบ

OCR container: แยกเป็น service/container เพื่อจำกัด CPU, RAM และเวลาได้ แต่ไม่จำเป็นต้องมีเครื่องจริงแยกในระยะแรก เริ่มบน Docker host เดียวแบบ resource-bounded; pilot ตั้งต้นราว 2 vCPU/4 GB RAM และ concurrency 1 งานเป็นสมมติฐานสำหรับวัดผล ไม่ใช่ sizing ที่รับประกัน

คิวงานหลาย tenant

เอกสาร 1,000 ไฟล์จาก 100 tenants ไม่ควรถูกประมวลผลพร้อมกันทั้งหมด ใช้คิวกลางที่แยก tenant, จำกัดงานพร้อมกันต่อ tenant (เริ่ม 1–2), จำกัดจำนวน worker รวม และใช้ fair scheduling/priority พร้อม aging เพื่อไม่ให้งานรอนานไม่สิ้นสุด

แสดงสถานะ queued / processing / needs review / completed / failed ให้ผู้ใช้เห็น; เพิ่ม worker ตาม queue wait, throughput, memory และต้นทุนที่วัดได้ ไม่เพิ่มเครื่อง OCR เพียงเพราะจำนวนงานที่เข้าคิวสูงชั่วคราว

ใช้การแก้ของผู้ใช้ให้รอบหน้าดีขึ้น โดยไม่เผยความลับ

ขอบเขตเก็บอะไรได้ข้อห้าม/การควบคุม
ความจำของ tenantชื่อหัวคอลัมน์ที่ tenant ใช้, alias ของ field, รูปแบบเอกสารหรือ mapping ที่ผู้ใช้แก้และยืนยันแล้วแยก tenant ชัด; ห้ามนำราคา, จำนวน, SKU, วันที่ หรือค่าธุรกรรมจากเอกสารเก่ามาเติมเอกสารใหม่
ความรู้กลางของแพลตฟอร์มเฉพาะ pattern ที่ทำให้ไม่ระบุตัว tenant/คู่ค้าและผ่านการตรวจ เช่น synonym ทั่วไปของชื่อ fieldปิดเป็นค่าเริ่มต้น; ต้อง opt-in ชัดเจน; ไม่เก็บต้นฉบับ ชื่อลูกค้า/ผู้ขาย SKU ราคา หรือข้อมูลระบุตัวบุคคล

เก็บ mapping ที่ยืนยันแล้วในฐานข้อมูลเชิงสัมพันธ์ได้ก่อน เพราะค้นตรงตาม tenant และอธิบาย audit ง่าย; ใช้ Qdrant เฉพาะเมื่อมีโจทย์ค้น pattern แบบ semantic จริง และเฉพาะข้อมูลที่ได้รับอนุญาต ไม่ใช่การ fine-tune model

การแก้ข้อมูลต้องเก็บแหล่งที่มา/ผู้ยืนยัน/เวลาและรองรับถอน consent กับลบข้อมูล เมื่อยกเลิกการแชร์กลาง ให้หยุด ingest ใหม่และลบหรือทำให้ข้อมูลที่แชร์ไปแล้วไม่สามารถย้อนระบุตัว tenantได้ตามนโยบาย

  • รับเฉพาะชนิดไฟล์ที่กำหนด และตรวจ MIME จริงกับ file signature; ปฏิเสธไฟล์ปลอม/ไม่ตรงชนิด, PDF เสียหาย, เข้ารหัส หรือมีรูปแบบไม่รองรับ; จำกัด bytes/pages/pixels/time/memory และ decompression
  • สแกน malware เป็นชั้นหนึ่งเท่านั้น; ประมวลผลด้วย parser ที่อัปเดตใน isolated, non-root worker, read-only filesystem, ไม่มี network egress และจำกัด CPU/RAM/time; ห้าม worker เปิด URL หรือเรียก GIS/provider เอง
  • PDF: ตรวจและตัด JavaScript, launch/action, embedded files, forms และ external references; สร้าง preview ที่ปลอดภัย (เช่น render เป็นภาพ) ไม่เปิดไฟล์ต้นฉบับที่ยังไม่ผ่านการทำให้ปลอดภัยใน browser
  • ภาพ: decode แล้ว encode ใหม่เป็น PNG/JPEG ที่อนุญาต ลบ metadata และปฏิเสธ SVG/ไฟล์ polyglot ใน pilot; คุมจำนวน pixel เพื่อกัน decompression bomb
  • ข้อความหรือภาพในเอกสารเป็น untrusted data รวมถึง prompt injection ที่สั่งให้เปิดเผยข้อมูลหรือเรียก tool; แยกเนื้อหาเอกสารออกจาก system instruction, model ไม่มี GIS credential/tool โดยตรง และ output ต้องผ่าน schema/code validation
  • หยุดและส่งให้ผู้ใช้ตรวจเมื่อพบ active content, parser error, ประเภทไม่แน่ใจ หรือข้อมูลขัดแย้ง; antivirus อย่างเดียวไม่ใช่หลักประกันว่าไฟล์ปลอดภัย
  • ส่งข้อมูลไป provider ได้เฉพาะที่ deployment/tenant policy อนุญาต; ไม่ log file content หรือ PII
  • ระบุ retention และลบไฟล์ต้นฉบับ/OCR/extraction ตามอายุข้อมูลและคำขอลบ
  • ไม่ส่งเอกสารเข้า Qdrant, RAG, training หรือ shared dataset อัตโนมัติ; ต้องมี authorization flow แยก
  • ใช้ duplicate detection + idempotency + single-use confirmation; ผลเขียนไม่ชัดให้หยุดเป็น unknown ไม่ retry เอง

ทำทีละระยะ เพื่อลดความเสี่ยง

Phase 0 · Discovery

เลือกเอกสาร Purchase และเก็บตัวอย่าง

เลือกชนิดเอกสาร/ทิศทางของ Purchase ที่จะเริ่ม, transaction flow, format, ภาษา, retention และ provider policy; สร้างชุดเอกสาร anonymized ที่มี expected values/evidence

Phase 1 · Sponsor chooses

เลือกหนึ่ง document family และทิศทาง

BD/PO ยังไม่เลือก pilot; Supplier quotation → PO preview เป็นเพียงทางเลือกเชิงเทคนิคที่ต่อกับระบบปัจจุบันได้ ไม่ใช่การยืนยันมูลค่าธุรกิจสูงสุด

Phase 2 · Expand

ขยายทะเบียนชนิดเอกสาร

เพิ่มแต่ละ document type ผ่าน registry: schema, aliases, validation, evidence, evaluation fixtures, owner และ GIS mapping; แยกสถานะรู้จัก/ดึงข้อมูล/preview/write; เพิ่ม XLSX/DOCX parser เมื่อผ่าน security/quality checks

Phase 3 · Operations

Batch และการจัดการข้อยกเว้น

queue/progress, idempotent retry, bulk review, dashboard, retention automation และ cost/quality monitoring

ไม่ควรเริ่มด้วย “รองรับทุกเอกสาร” เพราะชนิดเอกสารแต่ละแบบมีความหมาย, required fields และ GIS actions ไม่เหมือนกัน

วัดอะไร ก่อนจะขยาย

ตอนนี้ยังไม่มี baseline จากชุดเอกสารธุรกิจจริง จึงควรเก็บค่าพื้นฐานก่อนตั้ง target

Classification

ชนิดเอกสารถูกต้อง, unknown rate, อัตราผู้ใช้เปลี่ยนประเภท

Extraction

critical field exact match, line item precision/recall, evidence coverage

Operator

อัตราแก้ข้อมูล, เวลาถึง preview, preview rejected/duplicate

Operations

cost/document/page, p50/p95 latency, retry/failure/manual fallback

Safety gates

ข้าม tenant = 0; เขียนก่อนยืนยัน = 0; invented GIS values = 0

Test set

หลาย layout, scan, ภาษา, currency/date, missing/conflict, duplicate, malformed, malicious file

เรื่องที่ต้องนิยามก่อนเริ่มทำ

  1. เอกสาร Purchase ชนิดไหนและทิศทางใด? PU หมายถึง Purchase แล้ว แต่ยังต้องระบุว่าเป็นเอกสารใด เช่น supplier quotation, PO หรือเอกสารซื้อชนิดอื่น และนำเข้าจากฝั่งไหน
  2. เริ่มจาก flow ใด? BD/PO ยังไม่เลือก pilot; Supplier quotation ขาเข้า → PO preview เป็นเพียงทางเลือกเชิงเทคนิค
  3. ไฟล์ pilot: PDF + PNG/JPEG ก่อน หรือรวม Excel/Word ตั้งแต่รอบแรก
  4. Data policy: retention เท่าไร และส่งไฟล์/ข้อความให้ external AI provider ได้หรือบังคับ local
  5. Evaluation: เตรียมเอกสารตัวอย่างที่ anonymize แล้วพร้อมคำตอบจริงเพื่อสร้าง gold set
สถานะ BD/PO: เห็นตรงกันที่ `validate_first`; PO ปรับข้อเสนอหลัง BD review และไม่เลือก PO/quotation เป็น pilot โดยไม่มีหลักฐาน จึงยังไม่ตั้งราคา/ROI/target
